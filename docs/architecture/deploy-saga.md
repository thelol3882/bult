# Deploy as a saga

bult is a distributed system even without microservices. A deploy changes state in four independent places, and no transaction spans them:

| Resource | Where its state lives | Has its own "commit" |
|---|---|---|
| Control plane | PostgreSQL (apps, deploys) | a database transaction |
| Builder | job directory on the build node (`status.json`, `build.log`) | the job reaches a final state |
| Runner | a container in Docker on a worker node | the container is created and started |
| Ingress | `/routes` volume + nginx | the sidecar confirms a generation in `status.json` |

Docker on a node cannot roll back together with Postgres, so two-phase commit is not an option. Instead, a deploy is a **saga**: a sequence of local transactions where a failure is handled by **compensating actions** for the steps already done, in reverse order.

## Orchestration, not choreography

The deploy worker (`app/deploys/services/worker.py`, steps in `runner.py`) in the control plane is the saga **orchestrator**: one coordinator drives every step and decides what to do on failure. The alternative, choreography (each participant reacts to the others' events), hides the control flow across components; at our scale one explicit coordinator is easier to reason about and to test.

## Steps and compensations

| # | Step (local transaction) | Compensation if a later step fails | Status |
|---|---|---|---|
| 1 | `StartDeploy` → image pushed to the registry | `CancelDeploy` while still building; a finished image is left (harmless, garbage-collected later) | done: user cancel (below); `CancelDeploy` is not yet a compensation for a failed later step |
| 2 | `RunReplica` × N → containers running on nodes picked by the scheduler (`nodes.md`) | `RemoveReplica` for each | done — on route failure, on any error after the replica started, and when the app is deleted mid-deploy (not when the lease was lost: the replica then belongs to the new owner) |
| 3 | apply routes → sidecar confirms the generation | the sidecar itself swaps `current` back when `nginx -t` fails | done |
| 4 | deploy marked `running` | — | done |
| 5 | older `running` deploys of the app marked `superseded`, their replicas removed (redeploy) | none: past the pivot, failures are only logged | done |

**Redeploy** has a pivot: the old replicas of the app are removed only **after** the route points at the new one and the new deploy is written `running`. Before the pivot every step is compensated by undoing it; after the pivot the saga only moves forward. So a redeploy has no downtime, and a failure to remove the old replica never touches the new deploy: the old deploy is already `superseded` and the leftover replica is removed by the startup garbage collection (below).

## Prerequisites already in place

- **Idempotent steps.** A saga retries. `deploy_id` and `replica_id` are generated by the control plane before the first call, so a retried `StartDeploy`/`RunReplica` reaches the same job/replica instead of creating a duplicate (see `agent-api.md`, idempotency and error codes).
- **Idempotent compensations.** `RemoveReplica` of a replica that does not exist returns OK ("desired state" semantics), so a compensation can be retried safely too.
- **Deadlines with "outcome unknown".** `DEADLINE_EXCEEDED` means the step may or may not have happened; idempotency makes "retry with the same id" the safe answer.

## The saga log and recovery

The `deploys` table is both the **saga log** and the **work queue**: a deploy in `queued`, `building` or `starting` is unfinished work. `POST /apps/{name}/deploys` only inserts a `queued` row and answers 202; no gRPC call happens in the request. A partial unique index (`app_name` where status is active) allows one active deploy per app, so a second POST fails with `409 deploy_in_progress` (the check cannot live in the service: two requests would both pass it across an `await`).

**Claim and lease.** A worker loop in the API process (started in the lifespan) polls about once a second. A claim is one short transaction: take the oldest active deploy whose lease is empty or expired (`FOR UPDATE SKIP LOCKED`), set `lease_owner`, `lease_until = now + 30 s`, `attempts + 1`, commit. Up to 4 deploys are processed concurrently, each in its own task. The row lock is never held across gRPC calls; the lease is what says "this deploy is being worked on".

**Heartbeat.** While a deploy is processed, a heartbeat renews the lease every 10 s. If a renewal reports that the lease is no longer ours, the work task is cancelled.

**Fencing.** Every status write is `UPDATE ... WHERE id = :id AND lease_owner = :me`. Zero rows means the lease was taken (or the app was deleted): the worker stops and writes nothing more. A worker that stalled past its lease therefore cannot overwrite what the new owner did. The route step also re-checks the owner under the routes lock before publishing.

**Crash and shutdown.** A crashed process simply stops renewing; after the lease expires the deploy is claimed again (by this process after a restart, or another one). A graceful shutdown cancels the work and releases the held leases (`lease_until = NULL`, and the attempt is given back), so a restart picks the deploys up at once. After `attempts > 3` the next claim marks the deploy `failed` ("gave up after 3 attempts"): a deploy that keeps killing its worker must not loop forever.

**Resume by status.** Steps are idempotent, so a claimed deploy continues from its status:

| Status | What the worker does |
|---|---|
| `queued` | `StartDeploy` (idempotent by `deploy_id`; one retry on `DEADLINE_EXCEEDED`) → `building` |
| `building` | poll `GetDeploy`: still running → keep polling; `SUCCEEDED` → `starting` with commit and image; `FAILED` → `failed` with the build error; `NOT_FOUND` → `failed` "build lost" |
| `starting` | `ListReplicas` on the runners looks for `{deploy_id}-r0 … r{N-1}`: those found running are reused (and recorded), the missing ones get `RunReplica` (idempotent by `replica_id`) on the node the scheduler picks; then publish the route → `running` |

**Startup check.** Once at startup (alongside the worker), the replica rows that no reachable runner has are retired; a `running` deploy left with no replica becomes `failed` ("replica is gone"), one with some left stays `running` with a lower `ready/desired`. Then the routes are re-applied from the database, ignoring node health (the node monitor judges that once the agents have reported; see `nodes.md`). A runner that does not answer is logged and its replicas are left alone: silence is not proof that a replica is gone. Bringing such a deploy back up is a separate feature.

**Garbage collection.** In the same startup check, every replica on a reachable runner that no live deploy lists is removed: the replicas of a deploy that is not `running` (or has no row), and the extras of a running deploy (a scale-down whose removal failed): the leftovers of a redeploy whose cleanup failed, of a stop, or of a database wipe. Replicas of deploys still in flight (`queued`, `building`, `starting`) are kept, because a resumed deploy reuses its replica; replicas whose name is not `<deploy_id>-r<n>` are not touched; a node that does not answer is skipped.

Compensations: `RemoveReplica` for every placed replica on route failure, on any error after a replica started, and when the app is deleted mid-deploy.

## Several replicas

A deploy wants `desired_replicas` (the app's `replicas`, at least 1) and the `starting` step ensures them one by one, each on the node the scheduler picks (`nodes.md`). The outcome is decided by how many came up:

| Replicas started | Result |
|---|---|
| all | `running`, `ready/desired` = `N/N` |
| some (≥ 1) | `running` with a lower count (`2/3`); the replicas that started are **kept**, not rolled back: a half-capacity app is better than none, and the missing replica is added by scaling to the same count |
| none | `failed` with the last error; nothing to compensate (a replica that did start before a later route failure is removed, see above) |

The route step publishes one upstream with every started replica on a ready node; if none of them is on a ready node the deploy fails like a route failure. A redeploy is blue-green for all N: the new replicas start next to the old, the route switches to the new set, then all old replicas are removed. A resumed deploy finds the replicas that already run and only places the missing ones.

Replica rows are written right after each `RunReplica`, so a deploy that is resumed or scaled sees where its replicas are without asking every node.

## Final writes and the lease

A write that ends the worker's job (`running`, `failed`, `superseded`) clears `lease_owner` and `lease_until` in the same fenced `UPDATE`. A heartbeat that finds its lease gone checks whether the deploy is finished (final status, empty owner) before treating it as taken: cleanup after the pivot, e.g. a slow `RemoveReplica`, must not be cancelled by the worker's own final write.

## Deploy from an image: start and rollback

A deploy is normally `queued → building → starting → running`. A deploy created **from an image** starts at `starting` with the `image` and `commit_sha` of an earlier deploy and `source_deploy_id` pointing at it; the worker skips `StartDeploy` and `GetDeploy` and goes straight to `RunReplica`. Everything after that (route, `running`, pivot) is the same saga, and the partial unique index still allows one active deploy per app.

| Operation | Source image | Effect |
|---|---|---|
| `POST /apps/{name}/deploys` | built from the repository | normal deploy; a stopped app becomes wanted again |
| `POST /apps/{name}/deploys/{id}/rollback` | that deploy | refused with 409 unless it reached `running` and has an image |
| `POST /apps/{name}/start` | the newest deploy that reached `running` | 409 if there is none, or if the app is already running; N = the app's `replicas`, at least 1 |
| `PUT /apps/{name}/replicas` | the running deploy; for a stopped app the newest that reached `running` | no build; adds or removes replicas of the same deploy (see `nodes.md`) |

A deploy "reached running" when it has an image and `ran` is set (written together with `running`). A registry that has garbage-collected the image makes `RunReplica` fail, and the deploy ends `failed`.

## Cancel

`POST /apps/{name}/deploys/{id}/cancel` (owner only, 202). `cancelled` is a final status and is not active, so the app is free for the next deploy.

| Deploy status | What happens |
|---|---|
| `queued` | One conditional write: `status = 'cancelled' WHERE status = 'queued'` and no live lease, lease cleared. No agent call. If the row no longer matches, the worker took it between the read and the write: the request falls through to the `building` path. |
| `building` | `CancelDeploy` on the builder, answer 202. The worker, still polling, sees `CANCELLED` from `GetDeploy` and writes the final `cancelled` (lease cleared like any final status), never `failed`. |
| `starting` | 409 `deploy_not_cancellable`: the image is built and the replica is almost up; undoing it is the stop path, not a cancel. |
| `running`, `failed`, `cancelled`, `superseded`, `stopped` | 409 `deploy_not_cancellable`. |

Two details. A `queued` row with a live lease was claimed but has not written `building` yet; cancelling it in place would let the worker overwrite `cancelled` with `building`, so it is treated as taken, and when the builder does not know it yet (`NOT_FOUND`) the answer is a 409 "try again in a moment". If the builder reports the build already `SUCCEEDED`/`FAILED`, the answer is 409 too. A builder that does not answer is 503 `builder_unavailable`.

## Stop

`apps.replicas` is the desired state (`0` stopped, `1..5` running). `POST /apps/{name}/stop` is refused while a deploy is in progress, then: `replicas = 0`, the running deploys become `stopped` (a final status), their replica rows are retired, the routes are re-applied (the app gets the stopped page, see `ingress.md`), and only then are all the containers removed (best effort). Each step is its own transaction in its own domain; the order is chosen so that a failure in the middle leaves a state the startup check repairs.

## Deleting an app

Deleting an app is also a saga across the same resources: the app's data, its routes, its replicas on the nodes. The order matters: a step that cannot be undone, or that would leave users facing a broken address, must come as late as possible. The intended order is not decided yet.

The place where the compensations run is the `AppDeleted` handler (`app/deploys/handlers.py: on_app_deleted`): `AppService.delete` removes the app and publishes the event; the handler, delivered synchronously after commit and before the 204, forgets the app's deploys, re-applies the routes without it, then removes the app's replicas (route update and `RemoveReplica` are best effort and logged). The replicas are found by asking every runner node (`ListReplicas`, filtered by `app_id`), not from deploy rows: the `ON DELETE CASCADE` foreign key has already removed the rows at commit. This also removes superseded replicas left by earlier redeploys; a node that cannot be reached is logged and skipped. A deploy still in flight notices on its own that its row is gone (its fenced write matches nothing and the row is missing) and removes its replica itself (see `runner.py`).

## Why not a distributed transaction

| | 2PC / XA | Saga |
|---|---|---|
| Participants must support prepare/commit | yes — Docker, nginx and the file system do not | no — only idempotent steps and compensations |
| Locks held across the network during the transaction | yes | no |
| Intermediate states visible | no | yes (`building`, `starting`) — acceptable and even useful for a deploy |
| Complexity | in the infrastructure | in the orchestrator code (explicit and testable) |
